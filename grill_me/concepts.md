# Concept ledger

Cross-repo curriculum of transferable software-engineering concepts. Unchecked = still in retest rotation. See "The concept ledger" in SKILL.md for the rules.

- [ ] Idempotency keys — a caller-chosen key on a remote mutation makes crash-retry safe by construction: the retry returns the original result instead of acting twice (introduced 2026-07-07, Stripe subscription create / dual-write crash)
- [ ] Dual-write problem — two systems, no atomic commit: any crash between the writes strands one side; mitigations are idempotent remote calls, write-ahead intent records, and reconciliation (introduced 2026-07-07, Stripe create + local mirror)
- [ ] Webhooks are notifications, not state transfer — delivery is unordered and lossy, so treat an event as "something changed, go fetch the truth," never as the value itself (introduced 2026-07-07, refresh_status convergence design)
- [ ] Reconciliation sweeps — a periodic re-fetch of mirrored remote state demotes push delivery from single point of truth-transfer to latency optimization (introduced 2026-07-07, missed-webhook drift past Stripe's ~3-day retry window)
- [ ] Dunning / smart retries — the post-failed-charge collections process (retry schedule, customer emails, terminal action), configured provider-side and invisible in the codebase (introduced 2026-07-07, past_due grace design)
- [x] Signed-webhook replay defense — HMAC over the raw bytes plus a signed-timestamp tolerance window (~5 min); dedup/idempotency only has to cover replays inside the window (introduced 2026-07-07, construct_event; nailed 2026-07-11, designed the fix for BookLM's internal API from the verifier side)
- [x] Test your model of the contract — you can't test a third party's code, but you must test your assumptions about it: recorded cassettes (VCR), provider mocks (stripe-mock), pinned API versions turn contract drift into visible diffs (introduced 2026-07-07, hand-rolled Stripe fixtures gap; nailed 2026-07-11, proposed pinning cross-language HMAC signers via recorded signatures)
- [ ] Stored state vs. computed state — a stored high-water mark records history and decouples past completion from present rules, at the cost of drift; computed state can't drift but makes regression an implicit side effect of a deploy instead of an explicit, reviewable decision (introduced 2026-07-07, onboarding_stage frontier)
- [ ] Idempotence by convergence, not locking — concurrent duplicate processing is safe when the handler writes a pure function of current source-of-truth state; you don't need a mutex, you need convergent writes (introduced 2026-07-07, concurrent webhook delivery)
- [ ] Fail-open vs. fail-closed defaults — opt-out gating (before_action + skip) fails closed, the right direction for access control; know which way every guard fails before you need it to (introduced 2026-07-07, app-wide subscription gates)
- [ ] Negative invoice mechanics — provider credits don't refund to the card; negative totals become account credit balance and amount-due floors at zero, so "you'll be credited X" UIs must read the total, not amount_due (introduced 2026-07-07, downgrade proration preview)
- [ ] Ruby `module_function` — marks a module's methods as both private instance methods and module-level singletons, the idiom for stateless function-bag modules (introduced 2026-07-07, Onboarding::Steps registry)
- [ ] Lock-then-lease claim pattern — a row lock (FOR UPDATE SKIP LOCKED) protects only the instant of claiming; a persistent lease column (locked_at) protects the processing window after commit — and dead workers strand leases, which is why every lease needs a reaper (introduced 2026-07-11, ingestion_tasks claim)
- [ ] Check-then-act (TOCTOU) races — a guard that reads state then writes lets two concurrent actors both pass the check before either acts; the fix is making the check part of the act (conditional UPDATE ... WHERE status = ?, rows-affected as the verdict) (introduced 2026-07-11, transition_from! failed/ready race)
- [ ] Definite-assignment reasoning + try/except/else — prove a variable is bound at point P by enumerating every control-flow edge into P; Python defers this to runtime, so encode "only on success" structurally with `else` and let pyright/ruff re-run the proof on every edit (introduced 2026-07-11, `written` in process_task)
- [ ] Defensive defaults must fail loud, not plausible — pre-initializing with a normal-looking value (written = 0) converts a crash into silently wrong data; prefer structure that forbids the state, then static analysis, then a sentinel that blows up (None), never a plausible default (introduced 2026-07-11, same process_task thread)
- [ ] Idempotency-by-constraint requires a deterministic producer — ON CONFLICT DO NOTHING is only a true no-op if re-runs produce identical rows; a nondeterministic producer partially retried yields spliced/frankenstein data, so switch to delete-then-insert in one transaction or a fresh version key per attempt (introduced 2026-07-11, chunks unique index)
- [ ] Fair queuing lives in the claim query — in a SQL-polled queue the scheduler IS the ORDER BY; per-user round-robin = stamp each task with a per-user sequence number and ORDER BY (user_seq, created_at), interleaving everyone's Nth items (introduced 2026-07-11, bulk-upload starvation)
- [ ] Event monitors can't see stuck states — a lost report or dead worker raises no exception for Sentry to capture; stranded rows are a *state*, caught only by a periodic threshold sweep over the DB (which is also the reaper's skeleton: one query, alert arm + repair arm) (introduced 2026-07-11, stuck-in-processing forensics)
- [ ] Transaction boundaries bound observability — atomic writes mean intermediate states never exist to monitor (chunk count is 0 then N, never trickling); diagnosis plans must respect your own commit points (introduced 2026-07-11, "watch the count grow" miss)
- [ ] Capacity claims are checkable — "which resource exhausts first" arguments must be anchored to the actual config (puma.rb threads, dyno RAM), not defaults or generalities; open the file before committing to the bottleneck (introduced 2026-07-11, RAM-vs-Puma dispute)
- [ ] Direct-SQL from a second service couples at the table level — bypassing the ORM means hand-maintaining its behaviors (timestamps, validations, denormalization consistency) and coupling deploys to migrations with no contract test; the mitigations are least-privilege creds and golden-file contract fixtures (introduced 2026-07-11, worker INSERT_CHUNKS_SQL)
